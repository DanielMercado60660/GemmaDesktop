# MLX, agent donors, and Harness² — exploration round two

4 November 2026. Source-only exploration of the eight requested repositories, current Gemma guidance, the local integration, and the recorded campaign. This extends the [first exploration](exploration-2026-11-04.md). No backend was installed or started, weights downloaded, source behavior changed, or inference benchmark run. Recommendations below are experimental candidates, not measured speed or quality improvements.

The proposed direction is to keep ADK and the host-owned execution system, add a small interchangeable inference boundary, compare local model/backend combinations, and use Harness² to refine the strongest configurations. E4B deserves a deliberate experiment, not an assumption that a harness designed for 26B will suit it unchanged.

**Starting facts that affect the experiment**

- Existing `gemma4:12b-mlx` and `gemma4:26b-mlx` runs already used MLX through Ollama. Another MLX server can improve caching, decoding, scheduling, or protocol handling, but is not the first introduction of MLX.
- The recorded 72-trial campaign used **26B**, 65,536 requested context, thinking on, temperature 1, 16,384 output tokens, 80 steps, and a 1,200-second deadline. See the [frozen conditions](../implementation/HARNESS_CAMPAIGN.md).
- Read-only inspection found local Ollama manifests for 12B and 26B, but no E4B manifest in that Gemma directory. Their SHA-256 identities remain `ded7a27350032202d9e9b2a6071e8aa89959ab156771b5228f30863c741c4970` and `f0fc7e0ae4947d382989b1f57db3d098a86b87c5b6e9523b9561ba81a2a64879`. Manifest presence does not prove that every weight blob exists or that a model currently loads. No daemon version or live residency was rechecked.
- The app admits one inference at a time. For its current interactive loop, warm prefix reuse and compatible speculative decoding are more directly relevant than concurrent-request throughput. A faster complete tool loop is more useful than an isolated high tokens/second number.
- The local 26B manifest already includes draft-model tensors and configuration. Record whether/how the baseline actually uses that drafter before attributing a gain to newly introduced speculation; bundled weights alone do not establish active use.

Expert configurations use serial decode; dense-model batching claims should not be transferred to 26B. mlx-lm's [text architecture](https://github.com/ml-explore/mlx-lm/blob/736ab0d8c1d0edc79c3d798044fe6904e2fa23be/mlx_lm/models/gemma4_text.py) includes PLE and MoE, while its [wrapper](https://github.com/ml-explore/mlx-lm/blob/736ab0d8c1d0edc79c3d798044fe6904e2fa23be/mlx_lm/models/gemma4.py) strips multimodal tower weights. Text-agent support does not establish video/audio parity.

Packaging follow-up: the installed candidate uses the pinned stable [v26.11.1 release](https://github.com/ddalcu/mlx-serve/releases/tag/v26.11.1), whose tag resolves to [`ac00f9213214db94b96f1837282c1ce4ad9debc8`](https://github.com/ddalcu/mlx-serve/commit/ac00f9213214db94b96f1837282c1ce4ad9debc8) (1 November). The research revision `5b6fae449722…` is a later 4 November source head; findings from it are not proof of stable binary conformance. The vendor arm64 archive is 89,646,887 bytes with SHA-256 `9acaa7a21b294536c3db9f2683d85079727b4e8db725d34260020499523dc267`, matching `packaging/runtimes/inputs.json`. The app repackages verified regular files into its own archive and records that separate digest. mlx-serve remains protocol-unqualified until its exact packaged build/model/isolation path passes a real check.

The inspected mlx-serve [Ollama translation](https://github.com/ddalcu/mlx-serve/blob/5b6fae449722a5dd9b93a108ee3a6e01e8e3c8f5/src/host/api/ollama/translate.zig) ignores `num_ctx`/`keep_alive`, drops explicit `think:false`, and does not forward incoming thinking or tool-result names/IDs. It reports zero load duration and divides wall-clock intervals at the first chunk for prompt/decode timing. Those values are not interchangeable with the current Ollama metrics. Pointing the existing URL setting at it would therefore confound correctness and measurement.

oMLX has more explicit [usage fields](https://github.com/jundot/omlx/blob/4213c3284abc7b3746a91464a7af7ccc3732b759/omlx/api/openai_models.py), [Gemma conversion tests](https://github.com/jundot/omlx/blob/4213c3284abc7b3746a91464a7af7ccc3732b759/tests/test_gemma4_messages.py), and [disconnect tests](https://github.com/jundot/omlx/blob/4213c3284abc7b3746a91464a7af7ccc3732b759/tests/test_disconnect_guard.py). It still needs conformance work: its [Gemma converter](https://github.com/jundot/omlx/blob/4213c3284abc7b3746a91464a7af7ccc3732b759/omlx/adapter/gemma4.py#L169) strips leading thought blocks even on assistant tool-call messages and never copies separate `reasoning_content`. The [server's custom-extractor branch](https://github.com/jundot/omlx/blob/4213c3284abc7b3746a91464a7af7ccc3732b759/omlx/server.py#L4915) does not rescue that field. This is a concrete normalization mismatch: Google's distinction between completed-turn history and the active tool cycle is lost. First write a fixture containing both old turns and a current multi-tool cycle, then qualify a fix. oMLX remains an unqualified compatibility candidate. Optional server-side tool-result truncation also needs to remain disabled or explicitly represented.

The bounded architecture change would replace concrete generation dependencies around [client.go](../../internal/inference/client.go) and [adapter.go](../../internal/engine/adapter.go) with a local-provider contract for one generation stream. ADK keeps the loop; Go keeps tools, approvals, budgets and durable records. Generation, model management and embeddings should have separate capabilities, so a backend without model deletion or visual retrieval does not pretend to implement them. Preserve the existing single-inference admission initially.

**E4B, 12B, and 26B**

Here E4B means **Gemma 4 E4B**, not Gemma 3n E4B. Google's current model card describes E4B as 4.5B effective parameters with 8B including embeddings; 12B is dense; 26B A4B has 25.2B total and 3.8B active parameters. Consequently, model-name size alone does not predict speed or residency. Published LiveCodeBench results favor 26B over 12B, while the listed Tau2 score is slightly higher for 12B. These justify comparison, not a universal winner. [Google model card](https://ai.google.dev/gemma/docs/core/model_card_4).

| Model | Question to answer |
| --- | --- |
| E4B | Can a compact tool contract, concise observations and bounded recovery produce useful verified repairs with lower latency? |
| 12B | Does it offer the best balance of coding success, memory and complete-task time? |
| 26B A4B | Does its stronger published coding performance translate to better independently verified repairs here, at acceptable cost? |

E4B has a different thinking-off template from 12B/26B. Qualify auto/on/off and tool continuations per model. Do not inject the larger-model prefill into E4B. [Official thinking guide](https://ai.google.dev/gemma/docs/capabilities/thinking).

The [Ollama E4B MLX artifact](https://ollama.com/library/gemma4:e4b-mlx) and an [MLX-community instruction-tuned E4B artifact](https://huggingface.co/mlx-community/gemma-4-e4b-it-4bit) are available candidates. Artifact/template/quantization identities must be selected before benchmarking; different quantizations are different configurations. The community card's model/license metadata is not identical to Google's current metadata, so inspect the actual selected artifact's provenance and license when acquiring it. No weights were acquired here.

Start E4B with direct core coding tools rather than requiring a search step for every operation. Compare the same baseline harness across all models first; then measure a model-specific harness separately. E4B as an optional read-only specialist or as a first attempt with measured 26B escalation is a later routing experiment, after standalone behavior is known. Escalation cost and failed first attempts must remain in its accounting.

**Harness²: continue, with a more informative experiment**

The earlier result warrants continuing: automated passes and completion improved, while protected-input preservation regressed. Its recorded changes were:

| Measure | Baseline | Candidate |
| --- | ---: | ---: |
| Automated passes | 0/36 | 3/36 |
| Completed solver attempts | 28/36 | 34/36 |
| Incomplete attempts | 8 | 2 |
| Attempts with protected-input violations | 1 | 4 |

The [paired summary](../evidence/phase2-paired-evaluation-final-summary.json) and [independent review](../evidence/phase2-independent-promotion-review.json) support these counts. The small improvement justifies further investigation. It does not establish robust generalization: only one of the three passes was held out, supplemental probes found bugs in both Node passes, and cost accounting was incomplete. Historical gates and grades should remain unchanged.

The previous development comparison was particularly narrow: a matched one-task `python-ledger`, k=1 experiment for each method, with identical proposal content. It established integration parity, not that native versus upstream optimization had different efficacy. Current adaptation supports k=1 and a restricted declarative surface; increasing `k` in a command is not sufficient to add deeper recursion. Across tasks, the final candidate is the last composed revision, not an automatic synthesis of all prior revisions. These details are documented in the [operator guide](../implementation/HARNESS_CAMPAIGN.md) and implemented in [upstream_adapter.py](../../scripts/harness/upstream_adapter.py).

Use several representative development tasks, make composition explicitly preserve justified cross-task lessons, and review contradictions. First repair host-level protocol friction such as final verification and task-protected paths; then freeze that infrastructure for both arms. Harness² currently varies instructions, tool guidance, lessons and approved skill/workflow/delegate selections. Additional tunable options would require a reviewed schema extension. It should not compensate for dropped tool IDs or gain permission to rewrite its grader.

Upstream has advanced from the vendored `1cfe254e` to [`68688175`](https://github.com/google-research/harness2/tree/6868817518876de8fd170c6a8354daca273b6191). The [comparison](https://github.com/google-research/harness2/compare/1cfe254e8d25b15f37048c3730134686abe60335...6868817518876de8fd170c6a8354daca273b6191) includes task-input cache identity, proposer-failure accounting, retry-state preservation, incomplete-grade handling and explicit killed-rollout diagnostics. Review the core changes against our pinned adapter before an update; many benchmark/subprocess changes are outside our execution path. Do not import legacy-cache permissiveness merely because upstream retains it.

Our lesson compatibility already includes model digest, runtime version, method and capability hash ([lessons.go](../../internal/harness/lessons.go), line 100). A multi-backend extension should additionally identify backend, template/tokenizer and quantization/drafter configuration so lessons and cached results do not silently cross incompatible conditions. The paper's published gains use other model/harness combinations; they motivate the method, not a Gemma guarantee. [Harness² paper](https://arxiv.org/abs/2610.14224).

**A bounded experiment ladder for planning**

1. **Protocol probe before integration choice.** For each candidate, cover plain streaming, thinking on/off, exact multiline tool arguments, multiple calls and correctly matched results, current-tool-cycle thought retention, new-turn thought omission, context overflow, length truncation, cancellation during prefill/tool output, and truthful final usage. Inspect rendered model inputs when a conversion is uncertain. No tool executes until its complete stream passes host validation.
2. **Serving comparison with one model held fixed.** Start with the existing 26B baseline, or an explicitly recorded matched artifact available to all servers. Compare cold start, warm first token, repeated tool-turn prefixes, decode, memory and full-loop latency. Test cache/speculation switches independently; record drafter acceptance. Where weights or quantization cannot match, label the comparison as a configuration comparison rather than a pure backend speedup.
3. **Small model screen.** Proposed starting size: six representative development tasks × E4B/12B/26B × two fresh attempts = 36 runs. Use one qualified backend, frozen tools/executor and controlled settings; record all failures. This is screening, not promotion evidence. Include a tiny repair, multi-file change, unfamiliar API/schema use, verification recovery, longer-context recall, and read-only investigation.
4. **Targeted harness experiments.** For selected models, compare one mechanism at a time: focused tools, verification feedback/action, outcome-aware stall handling, resident read reuse, and bounded duplicate-result projection. Measure both benefit and negative controls. Then compose an E4B-oriented candidate and a quality-oriented candidate if the evidence supports two profiles.
5. **Harness² refinement and fresh qualification.** Run budget-matched Propose–Probe–Compose across multiple development tasks with an independent reviewer. Consider k>1 only after extending/testing the adapter and seeing that another iteration addresses a concrete failure. Preselect the candidate before new held-out exposure; independently author and freeze a new held-out pool. Never relabel the exposed old pool as unseen.

For every stage, retain backend/model/template/quantization identities, tool schemas, context and output limits, sampling settings, cache state, exact executor image, task bytes and all attempts. Use fixed seeds only where genuinely supported; cross-backend equal seed does not establish equal sampling. Counterbalance run order and separate residency effects from warm execution.

Report task correctness, fresh verification, protected-file preservation, completion, repeated/invalid calls, recall, wall time and measured tokens as separate outcomes. Timing should distinguish queue/load, prompt processing, decode, tools and verification; never substitute estimated intervals for provider-native metrics without labeling them. The headline product metric should be **verified tasks per unit time, including failed-attempt effort**, with correctness and integrity gates. A fast failed patch is still a failed task.

The immediate planning deliverable should therefore be a small provider-conformance prototype plus a reproducible diagnostic runner. That unlocks meaningful MLX, model and Harness² comparisons while retaining the established desktop and execution foundations.
