# Gemma 4 thinking and runtime follow-up — October 27, 2026

This targeted, read-only review followed realistic coding runs that produced repeated tool proposals and long, repetitive thinking without further workspace actions. It compared the installed Ollama version with the current official stable release, focusing on the Gemma renderer/parser, MLX sampling, generation limits, and tool handoff stops. It did not run inference, change application source, install or update Ollama, restart a server, or modify global runtime configuration.

**Finding:** explicit `think:false` is supported by the installed runtime and is a justified qualification variant. The reviewed upstream changes do not establish that updating Ollama would fix the observed degeneration. A positive `num_predict` bounds generated tokens in the pinned MLX decoder; it is separate from the requested context size and the overall request deadline.

## Thinking control on the installed version

In 0.32.3, ChatHandler replaces an omitted `think` value with `true` when the model advertises thinking. Explicit `false` survives that branch. Therefore the application's prior unspecified setting invoked thinking; omission was not equivalent to disabling it. Current Ollama documentation also describes boolean controls, but the pinned handler is the authority for the installed version. [Pinned handler](https://github.com/ollama/ollama/blob/fce745fe5e4f0c7741ca46fc5484c9471c997d00/server/routes.go#L2621), [thinking API](https://docs.ollama.com/capabilities/thinking).

The installed manifest specifies renderer and parser `gemma4`. Before rendering, the pinned server resolves model names containing `12b` to `gemma4-large`. That renderer omits the system `<|think|>` trigger when thinking is false and adds an empty thought block to an ordinary generation prompt. It also omits the thinking prefill after a tool response when thinking is false. Google's Gemma guidance explicitly documents the empty block for 12B/26B/31B as a way to suppress ghost thought channels. No manual control-token injection by Gemma Desktop is needed. [Name resolution](https://github.com/ollama/ollama/blob/fce745fe5e4f0c7741ca46fc5484c9471c997d00/server/renderer_resolution.go#L34), [renderer selection](https://github.com/ollama/ollama/blob/fce745fe5e4f0c7741ca46fc5484c9471c997d00/model/renderers/renderer.go#L96), [prompt generation](https://github.com/ollama/ollama/blob/fce745fe5e4f0c7741ca46fc5484c9471c997d00/model/renderers/gemma4.go#L138), [Google thinking guidance](https://ai.google.dev/gemma/docs/capabilities/thinking).

There is an observability limitation: when thinking is disabled, the parser silently discards any thought-channel text the model nevertheless generates. Absence of visible `message.thinking` is consequently insufficient proof of zero thinking computation. Assess elapsed time, terminal generation counts, finish reason, valid tool actions, and independently checked task results. [Pinned parser initialization and filtering](https://github.com/ollama/ollama/blob/fce745fe5e4f0c7741ca46fc5484c9471c997d00/model/parsers/gemma4.go#L64).

The newer renderer's thinking metadata declares boolean values, and its internal default is false. However, the newer server explicitly preserves the historical default-on behavior for local thinking-capable renderers. Reading the renderer's metadata alone would incorrectly suggest that an upgrade automatically disables thinking. [Stable renderer metadata](https://github.com/ollama/ollama/blob/675150d6ad2747df1e218ef59de9194bc4a7e538/model/renderers/gemma4.go#L855), [effective local thinking contract](https://github.com/ollama/ollama/blob/675150d6ad2747df1e218ef59de9194bc4a7e538/server/model_thinking.go#L64).

## Generation bounds and tool handoff

The pinned MLX `Prepare` method caps a positive `NumPredict` to the remaining architectural context. A nonpositive value instead permits generation up to that remaining capacity. The decode loop counts generated tokens, including thinking, against the positive limit. Thus an 8,192-token generation cap has a concrete enforcement path on 0.32.3. It does not bound prompt prefill time, guarantee an answer within that cap, or make `num_ctx` a hard MLX context limit. The task deadline remains necessary. [Preparation](https://github.com/ollama/ollama/blob/fce745fe5e4f0c7741ca46fc5484c9471c997d00/x/mlxrunner/pipeline.go#L27), [decode stopping](https://github.com/ollama/ollama/blob/fce745fe5e4f0c7741ca46fc5484c9471c997d00/x/mlxrunner/pipeline.go#L215).

The inspected local generation configuration supplies EOS IDs `[1,106,50]`. The local tokenizer maps those to `<eos>`, `<turn|>`, and `<|tool_response>` respectively; `<tool_call|>` is ID 49. The pinned tokenizer loader prioritizes generation-configuration EOS values, and decoding checks `IsEOS`. This review found no obvious missing tool-handoff stop in the model metadata. It does not prove that a particular generation will emit the expected stop token or identify the root cause of a repeated proposal. [EOS loading](https://github.com/ollama/ollama/blob/fce745fe5e4f0c7741ca46fc5484c9471c997d00/x/tokenizer/tokenizer_load.go#L202), [EOS check](https://github.com/ollama/ollama/blob/fce745fe5e4f0c7741ca46fc5484c9471c997d00/x/mlxrunner/pipeline.go#L239).

## Application qualification variant and limits

The new application controls are being qualified with **explicit thinking OFF, an 8,192-token generation cap, and temperature 0.2**. The default thinking selection remains **Auto**, preserving runtime-default behavior. This document records support and the intended configuration; it does not declare that profile successful or make it the default. Preserve prior failed runs as evidence and associate any new result with its exact binary, model digest, runtime, fixture revision, and controls.

The local model parameters and official model page specify `temperature:1`, `top_k:64`, and `top_p:0.95`. Temperature 0.2 is therefore an application override. Keep it unchanged in the initial thinking comparison so that the result is not confounded by an additional sampling change. A later comparison with the published sampling configuration would be a separate variable; the available evidence does not show that it would cure repetition. [Official model configuration and guidance](https://ollama.com/library/gemma4:12b-mlx).

Acceptance must distinguish a bounded failure from task completion: record generation-limit termination as incomplete, retain valid action receipts, and independently verify the resulting files and tests. Lower visible thinking, fewer tool proposals, or a faster final message alone does not establish correctness. Runtime upgrades, alternative models, and sampling changes require separate qualification rather than being presented as confirmed remedies.

**Bounded recommendation:** if the review-assisted 12B task remains unsuccessful, qualify **26B MLX first**, then 31B if needed. This starts with the slightly smaller artifact and a different MoE architecture; it is not a prediction of faster decoding or better results. Both are plausible single-model candidates on a 64 GiB Mac, but neither has a measured load/peak-memory result here. Weight storage, runtime conversions, bundled draft, KV/prefix caches, prefill buffers, macOS, and other apps all consume memory. Begin with one active model/request and the same 32K requested-context policy and bounded fixture; measure actual memory pressure, cancellation, and task correctness before increasing history. The pinned MLX context setting remains soft, so 32K is not a guaranteed cache-memory ceiling. Do not load both candidates concurrently or claim the 256K maximum fits based on artifact size.
