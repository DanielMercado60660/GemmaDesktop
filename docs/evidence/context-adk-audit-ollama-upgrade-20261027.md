# Ollama upgrade: 0.32.3 → 0.40.11

The upgrade is a material new experimental variable. It changes sampling defaults, tokenizer implementation and MLX cache handling. Its new thinking-discovery path preserves default On for these installed models. Those changes can affect the same saved request even when Gemma Desktop and model weights are unchanged. None establishes that the earlier coding failures are fixed. This audit made no inference requests, model downloads, installations or production changes.

The parent independently verified the installed client and running daemon as 0.40.11 after the user upgraded. This source audit compares official tags: [v0.32.3](https://github.com/ollama/ollama/releases/tag/v0.32.3), commit `fce745fe5e4f0c7741ca46fc5484c9471c997d00`, and [v0.40.11](https://github.com/ollama/ollama/releases/tag/v0.40.11), commit `675150d6ad2747df1e218ef59de9194bc4a7e538`. The official comparison reports 379 commits ahead. All four comparison pages were read; the GitHub changed-file listing caps at 300, so relevant tag files and commit patches were inspected separately. [Source manifest](context-adk-audit-ollama-upgrade-20261027.json).

## Gemma parser/template: what did not change

The exact `model/parsers/gemma4.go` tag diff is small: it stores the assistant-content-prefill predicate on the parser and adds `ThinkingClose()` for structured-output handling. Tool-argument parsing itself is unchanged; the Gemma parser test file has the same Git blob SHA in both tags. There is no source basis here for claiming that upgrading specifically fixes `run_command.args` strings instead of arrays, stale file hashes, or missing tool arguments. [Old parser](https://github.com/ollama/ollama/blob/v0.32.3/model/parsers/gemma4.go), [new parser](https://github.com/ollama/ollama/blob/v0.40.11/model/parsers/gemma4.go).

The late “Update gemma renderers” commit introduces an opt-in `gemma4-nemotron` variant that places assistant content before tool calls; it explicitly leaves Gemma4 auto-detection unchanged. Its changes to the ordinary renderer factor existing content rendering into a helper, while the new ordering is gated by the variant flag. It also adds Gemma4 target support for DFlash drafts. These are not proof of a changed ordinary 12B/26B tool transcript, and no evidence here establishes that these installed models use a DFlash draft. [Commit](https://github.com/ollama/ollama/commit/f52b9e742d8c9a308f7b23cd1f0ab52c7ddb694d).

New structured-output grammar work applies when a format/schema is requested. Gemma Desktop's ordinary native `/api/chat` tool loop does not become schema-constrained merely because it supplies tool definitions. Likewise, the upstream context-overflow compaction retry change is in the `/v1/responses/compact` implementation; it does not repair the application's independent ADK compaction. [Structured-output change](https://github.com/ollama/ollama/commit/5a0ff3116d7d1aff28cd7a390783d809f69f0b6c), [Responses compaction change](https://github.com/ollama/ollama/commit/1b45aa19dac5b42d97f345b8ba68bb8cf0b08cf8).

## Context and metrics

The inspected `server/prompt.go` files are byte-identical between these tags. The MLX client still describes its requested context as a soft limit and reports the lesser of that value and the model context. In both runners, the generation pipeline checks input tokens against the model's `contextLength`, then caps generated tokens by the remaining model context and requested `NumPredict`. This is not a newly fixed hard-requested-context guarantee. [Old client](https://github.com/ollama/ollama/blob/v0.32.3/x/mlxrunner/client.go#L228), [new client](https://github.com/ollama/ollama/blob/v0.40.11/mlxrunner/client.go#L289), [old pipeline](https://github.com/ollama/ollama/blob/v0.32.3/x/mlxrunner/pipeline.go#L27), [new pipeline](https://github.com/ollama/ollama/blob/v0.40.11/mlxrunner/pipeline.go#L28).

The old MLX pipeline already reports `PromptEvalCount: len(request.Tokens)`, so the forensic table's prompt counts are not merely uncached-token counts. The upgrade adds a separate `prompt_eval_cached_count` and retains logical input totals. Do not calculate new prompt-processing throughput from total logical prompt tokens when cache hits are present. [Metrics change](https://github.com/ollama/ollama/commit/855f4bf989da9e6b43b2c0af288e668e2105c00d).

Parent-captured `/api/show` metadata for both installed models reports `renderer: gemma4-large`, `parser: gemma4`, `template_source: renderer_parser`, thinking values false/true with default true, and model parameters temperature 1, top-k 64, top-p 0.95. Neither parameter string lists a repeat penalty. Model metadata reports a 262,144-token model context; that is separate from the application’s 32,768-token request. [Local capture](ollama040-model-metadata.json).

New `/api/show` metadata exposes effective `renderer`, `parser`, `template_source`, plus thinking values/defaults. The application can now record which source actually renders the prompt instead of assuming that a packaged Jinja template is active. [Metadata implementation](https://github.com/ollama/ollama/commit/36a6e994d2f6c4ab94b3555185154d069e5dba87).

## Qualification boundary

Keep every earlier report labeled as the 0.32.3 runtime. For any 0.40.11 trial, preserve model digest/configuration, effective renderer/parser/template source, all sampling controls, explicit thinking, output cap, context request, fixture revision and application version. Treat a successful new trial as evidence for that configuration, not retroactive proof that 32K context, ADK, or the old runtime alone caused the failures. The source changes warrant a controlled retest; this audit does not perform one.
